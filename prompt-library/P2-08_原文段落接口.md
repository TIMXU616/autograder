# 增补接口：报告原文段落 GET /api/v1/reports/{id}/text

契约于 2026-09-23 增补了 7.6 与业务码 4090（见 `docs/接口契约.md` 变更记录）。前端已按该形状实装，后端这边补实现。目标：结果页点某一评分项的证据，能跳到原文对应段落并高亮。

**只做这一件事。不许动评分逻辑（grader）、跑题兜底、evidence 校验、重试参数，也不许改动现有六个接口的形状。**

## 一、解析层：输出段落坐标

`app/services/parser.py` 的返回值增加 `paragraphs` 字段，形状为 `[{"start": int, "end": int, "text": str}]`：

- docx 按正文段落切分（表格行沿用现有拼接方式，视为段落）；pdf 按页切分。
- `start` / `end` 是该段在拼接后的 `text` 中的字符偏移，左闭右开。
- **硬约束：`text[start:end]` 必须与该段 `text` 逐字相等**，并且相邻区间首尾相接、不重叠、不留缝。
- **`text` 字段本身的内容必须与现在完全一致**——评分环节用的就是它，一个字符都不许变，只新增 paragraphs。

## 二、解析结果落库

现在解析结果只存在于内存，`/text` 接口需要能直接读到。二选一：

1. `reports` 表加两列 `parsed_text TEXT`、`parsed_paragraphs TEXT`（JSON 文本）；
2. 新增一张 `report_texts` 表。

选哪个在回传里说明理由。若选加列，按已有 comment / highlights / suggestions 的写法加 ALTER 兼容分支，兼容老库。解析成功时写入。

## 三、新路由

`GET /api/v1/reports/{report_id}/text`，返回：

```json
{"report_id": "...", "filename": "...", "text": "...", "paragraphs": [{"start": 0, "end": 20, "text": "..."}]}
```

分支与错误码：

- 报告不存在 → HTTP 404 + `{"code": 4042, "message": "报告不存在", "detail": {"report_id": "..."}}`
- `reports.status` 为 `uploaded` 或 `parsing` → **HTTP 200** + `{"code": 4090, "message": "报告尚未解析完成", "detail": {"status": "<当前状态>"}}`
- 解析失败的报告（解析类错误码 4003 / 4005）→ HTTP 200 + 对应业务码与文案
- 解析完成 → HTTP 200，**直接读落库结果，不得每次请求重新解析文件**

`app/constants.py` 补 4090 与它的 HTTP 映射（HTTP 状态 200）。

## 四、单测

原有 16 项期望值不变，新增三项：

1. **段落坐标自洽**：取任意 5 段，断言 `text[start:end] == 该段 text`，且第 i 段的 end 等于第 i+1 段的 start。
2. **未解析完成返回 4090**：用一个只上传、未触发评阅的报告调该接口，断言 HTTP 200 且 code 为 4090。
3. **报告不存在返回 4042**：随便给一个不存在的 report_id，断言 HTTP 404 且 code 为 4042。

## 五、冒烟脚本

`scripts/smoke.py` 在轮询到终态之后加一步：调 `/text`，断言 `paragraphs` 自洽（首尾相接、逐段 `text[start:end]` 相等），打印段数与正文长度。最后一行仍须输出 `PASS`。

## 六、验收（逐条给证据）

1. pytest 全绿，把输出贴回来（应为 19 项）。
2. 冒烟脚本一次跑通，`PASS`，并把新增那一步的实际输出贴上。
3. 对同一份报告，`/text` 返回的 `text` 与评分时送入模型的正文一致：打印两者长度与各自前 100 字比对。
4. 未触发评阅的报告调 `/text` 得到 4090，不是 404。
5. 报告不存在得到 404 + 4042。
