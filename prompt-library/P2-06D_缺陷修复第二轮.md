# 后端缺陷修复（第二轮）

真机复跑结论先给：**HTTP 全链路已经通了**。我用仓库里的真 key（glm-4.7）跑了完整冒烟——上传 201 → 触发 202 → 轮询到 success、total_score=100.0、items=7、student 派生正确、comment 非空、最后 PASS。所以主干没问题，下面这些是补漏。

先修正我上一轮说错的一句话：我说「reports 表缺 student 列导致两个接口拿不到 student」——**只对了一半**。控制器在读结果时用 `Path(filename).stem` 派生 student，`GET /result` 实测能正确返回。所以**不需要加列**，要修的是成绩列表那一侧，见 P0-2。

只改指定位置，不要重写整份文件，不要动已通过的解析错误码、重试参数、并发信号量、时间戳写法。

## P0-1 跑题护栏在真模型上失效（上一轮已提，仍未修）

证据：`case_offtopic.docx` 在 glm-4.7 上跑出 `total_score=13.2`、`status=success`，第 6 项 5.7 分、第 7 项 7.5 分。同一提示词在对话层测是 0 分——模型不可靠，护栏必须后端兜底。

修法两层都做：

1. 提示词层：`backend/app/prompts/scoring_v1.md` 的护栏 2 里固定跑题警告文案，要求 warnings 第一条必须是 `报告内容与数据结构实验无关`。
2. 后端层（决定性）：`app/services/grader.py` 的 `_normalize` 加跑题兜底。判定：warnings 任一条包含 `无关`、`跑题`、`不是数据结构` 任一关键词。命中后强制所有 items 的 `score=0.0`、`level="absent"`、`status="graded"`、`confidence="high"`、`evidence=None`，`total_score=0.0`，并追加固定警告。
3. 补 pytest：假响应里 items 带非零分、warnings 带「无关」，断言全部清零。

验收：重跑 case_offtopic，total_score 必须为 0.0、七项全 absent、warnings 含固定串。

## P0-2 成绩列表缺 student

证据：实测 `GET /api/v1/grades` 返回项的键是 `[report_id, total_score, status, finished_at, filename, template_id, template_name]`，**没有 student**；而契约 5.5 GradeListItem 已含 `student | string | null`。

修法：`app/repositories/grading_repo.py` 的 `list_grades` 在组装每条记录时派生 student：`Path(filename).stem`，与 `GET /result` 用同一套口径（同一份报告两处派生结果必须一致）。

验收：/grades 每条带 student，且与 /result 的值相同。

## P0-3 脚本路径与 HTTP 路径状态不一致（新发现）

证据（直接查库）：

| report_id | reports.status | grading_results.status |
| --- | --- | --- |
| 8efdebf5… | uploaded | success |
| aeb544a6… | uploaded | success |
| fd7058d3… | uploaded | success |
| 9201da41…（走 HTTP 上传的） | success | success |

前三条是 `scripts/run_one_report.py` 灌进去的。`run_grading` 只 insert 了结果、没更新 `reports.status`，而 `get_result` 是以 `reports.status in TERMINAL` 判断要不要取结果的。

后果：这三条记录通过 `GET /result` 查会返回 `status=uploaded`、`items=[]`。C 用脚本灌数据后，B 在前端一个字都看不到，会以为后端坏了。

修法：`grading_controller.run_grading` 在 `insert_result` 之后补一行 `grading_repo.update_report_status(report_id, status)`，与 `_process_report` 保持一致。

验收：脚本跑完后 `GET /result` 能查到完整结果；再查一次状态对比表，两侧一致。

## P1-4 order 参数非法返回 415，违反契约

证据：实测 `GET /api/v1/grades?order=foo` → **HTTP 415** + `{"code":4001,"message":"order 取值非法"}`。`routes/grades.py` 用的是 `UnsupportedTypeError`，而 4001 映射 HTTP 415。契约已经收窄：4001 只表示「上传文件类型不支持」，查询参数类错误统一走 4002 + HTTP 400。

修法：`routes/grades.py` 的参数校验失败改抛 4002 对应的异常，HTTP 状态取 400；`app/constants.py` 里 4002 的场景映射要同时覆盖「文件超限 → 413」与「参数非法 → 400」，按触发点区分。

验收：`order=foo` → HTTP 400 + code 4002。

## P1-5 docx 解析无兜底，且无正文不报 4003（上一轮已提）

`_parse_docx` 没有 try/except：损坏的 docx 会抛 `BadZipFile` 变成 500，违反「解析层不许裸抛 500」；纯图片 docx 抽不出文字还继续进评分。

修法：包 try/except（异常含 encrypted/password → 4005，其余 → 4003）；docx 抽出文本去空白后少于 50 字 → 抛 4003，与 pdf 口径一致。补两个 pytest。

## P1-6 队列异常被静默吞掉，且队列不持久化（新发现）

证据：`app/controllers/grading_controller.py` 的 `_worker_loop` 里是 `except Exception: pass`。

后果有两个：一是非 `GradingError` 的异常（SQLite 写失败、KeyError 等）会让任务静默消失，报告永远卡在 `grading`，前端轮询到死也等不到终态；二是队列只在内存里，`--reload` 或重启后正在跑的任务全丢，那些报告同样永久卡在 in-flight 状态。

修法：

1. `except Exception` 分支里必须 `logger.exception` 记录，并把该报告置 `failed`（写一条 `error_code=5001` 的结果记录，或至少更新 reports.status 并记日志）。
2. 服务启动时扫一遍 `reports` 表，把 status 为 `parsing / parsed / grading` 的记录置 `failed` 并记日志——避免重启后卡死。

验收：人为制造一次异常，报告落到 failed 且有日志；重启服务后，原本 in-flight 的记录被置 failed。

## P2-7 四条小的

1. `score` 有时返回整数（`0`、`15`），契约要求 1 位小数：`_normalize` 里对每个 score 做 `round(float(x), 1)`，None 保持。
2. `llm_client._mock_chat` 只返回三个顶层键，补成六键（comment 给占位中文、两个数组给空数组）。
3. `_retry_timeout` 里若重试时返回 429 或 5xx，会直接落到 5001/5002 而不走过载退避，把这两类响应交回过载重试路径。
4. `upload_report` 先落盘再插库，幂等冲突时文件留在 `uploads/` 变成垃圾，改成冲突时清理刚写的文件。
