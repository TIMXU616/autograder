## 缺陷一（必修）：FastAPI 自带校验错误不走契约的错误体形状

证据：实测

```
GET /api/v1/grades?page_size=500 -> HTTP 422
{"detail":[{"type":"less_than_equal","loc":["query","page_size"],
            "msg":"Input should be less than or equal to 100","input":"500","ctx":{"le":100}}]}

GET /api/v1/grades?page=0 -> HTTP 422
{"detail":[{"type":"greater_than_equal","loc":["query","page"], ...}]}
```

契约第 6 节规定错误响应体统一是 `{"code": 业务码, "message": "人类可读信息", "detail": 可选对象}`，第 7.5 节的失败示例明确写的是 `{"code": 4002, "message": "page_size 最大为 100", ...}`。现在这类错误由 FastAPI 的 `RequestValidationError` 直接吐默认结构，等于 B 的前端要处理两种错误形状，C 照契约写的断言也过不了。

修法：在 `app/main.py` 里注册 `RequestValidationError` 处理器，把校验失败统一转换成契约错误体：

- 取第一个失败项，拼出中文 message，例如 `page_size 最大为 100`、`page 最小为 1`、`缺少必填字段 file`。
- 业务码用 `4002`，HTTP 状态用 `400`。
- 响应体形状与其它错误完全一致：`{"code": 4002, "message": "...", "detail": null}`。
- 顺带确认 `app/constants.py` 里 4001 只映射 415、4002 按场景区分 413 与 400，且 `main.py` 的 `GradingError` 处理器优先使用异常自带的 `http_status`，没有再回落到表里。

验收：`?page_size=500`、`?page=0`、上传时不传 `file`、不传 `template_id` 四种情况，全部返回 HTTP 400 + `{"code":4002,...}`，形状与其它错误一致。

## 缺陷二（必修）：docx 报错文案说成 PDF

证据：上传一个损坏的 docx 并触发评阅，结果是

```
status=failed　error_code=4003　warnings=['该 PDF 无文本层，无法解析']
```

文件是 docx，却提示「该 PDF 无文本层」。这是 docx 分支复用了 PDF 的异常类导致的。

修法：`NoTextLayerError` 支持传入 message；解析层按文件类型给文案：

- pdf 无文本层 / 加密 / 打开失败：沿用现有文案。
- docx 损坏、docx 抽不出正文（少于 50 字）：`该 docx 无可提取正文，请检查文件是否损坏`
- 错误码仍为 4003，不新增码。

验收：损坏 docx 的 warnings 里出现的是 docx 文案，不再出现「PDF」字样。

## 缺陷三（顺手清掉）：跑题兜底后多余的警告

现象：跑题用例兜底清零后，warnings 里多出一条「total_score 与各项之和不等，已按各项之和重算」。这条是兜底改写分数后才产生的差异，不是模型输出不一致，属于自说自话的噪音，会让看日志的人以为模型返回有问题。

修法：`_normalize` 里先记下模型原始 `total_score`，跑题兜底命中并清零后不再追加这条重算警告；非跑题情况保持原逻辑不变。

验收：重跑 case_offtopic，warnings 只含跑题相关的那两条，不再出现重算提示。
