# 代码真值源与部署口径

定于 2026-09-22，面向 A / B / C 三人。争议点：同一份契约下出现「仓库里的 backend」与「公网后端服务」两个可运行对象，需要明确谁说了算。

## 一、一句话结论

**一套代码，三个位置，仓库 `AutoGrader/backend/` 是唯一真值源。**

## 二、三个位置各自是什么

| 位置 | 角色 | 是否真值源 | 说明 |
| --- | --- | --- | --- |
| 仓库 `AutoGrader/backend/` | 交付源、验收源、部署源 | 是 | 交付材料里的源码仓库就是它；所有验收、部署、评审都以它为准 |
| LearnBuddy 工作区 | 写代码的地方 | 否 | 大赛要求 AI 工具使用留痕，代码在这里生成与迭代；每次产出必须回流到仓库 |
| 公网服务 `autograder-api.app.workbuddy.host` | 仓库某一次构建的运行实例 | 否 | 只是「把仓库某次构建跑起来」的结果，本身不构成第二套实现 |

## 三、为什么看起来像两套

两个来源会产生差异，都不是「两套实现」：

1. **构建落后**：公网实例是仓库某一次构建启动的。仓库更新后如果没有重新部署，公网就停在旧构建。判断方法看部署记录里的 commit。
2. **运行配置不同**：部署环境不带 `GLM_API_KEY`，后端自动走 mock 模式（每项固定 80%）；本机带 key 走 glm-4.7 真评分。**代码路径完全相同**，只有这一个配置差异。

## 四、纪律（三条，从今天起执行）

1. **任何代码改动都必须落到仓库**才算完成。只存在于 LearnBuddy 工作区或部署暂存目录的改动，视为未交付。
2. **部署只从仓库出包**，不允许从别处改完直接部署。每次部署在 `docs/部署记录.md` 追加一行：时间、对应 commit、是否带 key、冒烟结果。
3. **冲突时以契约为准，行为以冻结版实例为准**。若公网行为与仓库代码不一致，先查是不是构建落后；是落后就重新部署，不是落后就按 bug 走修复流程。

## 五、联调口径（给 B）

- 接口字段与错误码：以 `docs/接口契约.md` 与 `docs/openapi.yaml` 为准。
- 行为验证：用公网实例，我会把它与仓库冻结版对齐。
- 发现不一致：先报给我，我判定是构建落后还是真 bug，真 bug 进变更记录。
