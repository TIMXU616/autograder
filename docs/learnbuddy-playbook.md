## 1. 红线（先说清楚）

**不得伪造、拼接、臆造 LearnBuddy 对话记录。**
理由不是道德说教，是三个现实风险：

1. 评委只要追问一句「这个评分点的 prompt 你当时怎么调的、为什么这么改」，编的人答不上来；
2. 对话记录与仓库提交时间线必须对得上，时间戳矛盾一眼可见；
3. 一旦被认定为材料造假，是整个团队的成绩问题。

**正路**：真实使用 + 把真实过程整理清楚。下面全部内容都是在真实使用的前提下，让这 25 分拿得更足。

## 2. "使用深度"到底指什么（25 分拆解）

评委看的是**深度**，不是**次数**。逐条对照：

| 得分点 | 具体表现 | 我们要交付的证据 |
|---|---|---|
| **全生命周期覆盖** | 选题论证 → 需求 → 架构 → 编码 → AI 能力设计 → 调试 → 测试 → 文档 → 复盘，每个环节都有对话 | 对话记录按阶段归档，每个阶段至少 1 段 |
| **多轮迭代**（最能体现深度） | 同一个 prompt 从 v1 到 v2 到 v3，能看出"为什么改、改了之后好了多少" | 保留 prompt 的迭代版本对比 |
| **Skills / 资料库 / 记忆能力** | 不只当聊天框用：把报告素材、评分模板放进**资料库**，用它的**代码辅助** skill | 资料库截图 + 调用记录 |
| **三人都有真实记录** | 不是只有 A 一个人在用 | 三人的账号各有关键对话 |
| **成果绑定** | 作品里最核心的 AI 能力，就是 LearnBuddy 提供的 | AI 评分链路的 prompt 在 LearnBuddy 上打磨 |
| **可追溯** | 对话时间与 git 提交时间对得上 | 归档时标注日期 |

## 3. 工作方式切换：让 LearnBuddy 成为"主开发"

### 3.1 现状 vs 目标

| | 现状（要改） | 目标 |
|---|---|---|
| 谁写代码 | 本地直接产出 | **先在 LearnBuddy「代码开发」任务里要方案，它的产出落到仓库** |
| 谁定架构 | 本地拍板 | **LearnBuddy 给出方案 → 我们判断取舍 → 记录为什么这么选** |
| AI 评分链路 | 没开始 | **在 LearnBuddy 上迭代 prompt**（这是作品核心，也是最拿分的部分） |
| 出错怎么办 | 自己查 | **把报错原文丢给 LearnBuddy，让它定位** |

### 3.2 角色调整（三人）

| 角色 | 调整后职责 | 每日动作 |
|---|---|---|
| **A 主驾** | **LearnBuddy 主对话人**。需求、架构、AI 评分链路 prompt 迭代都在里面做 | 每天至少 2 小时泡在 LearnBuddy；每完成一段导出一次记录 |
| **B（你）** | 把 LearnBuddy 的产出**落成能跑的东西**：建文件、装依赖、跑起来；**把报错原文回喂给它**；部署 | 每遇到卡点，先问 LearnBuddy，再动手 |
| **C 数据** | **素材与质量的供给方**：把报告素材、测试用例、评分点标准放进 LearnBuddy 资料库；把测试发现的问题**转写成给 LearnBuddy 的提问** | 每次抽检发现评错，就在 LearnBuddy 里开一轮"为什么评错、怎么改 prompt" |

**核心规则一句话**：**任何技术决策，先在 LearnBuddy 里问过，再落到代码。** 这条规则执行 5 天，对话记录自然就有深度了。

### 4.4 阶段四：AI 评分链路 + Prompt 工程（**最能拿分的一段**）

**4.4.1 评分点模板设计**

```
我要设计实验报告的「评分点模板」，它是整个评阅系统的核心。
请针对计算机专业的《数据结构》实验报告，设计一套评分点模板，要求：

1. 5-8 个评分点，总分 100
2. 每个评分点给出：名称、分值、判定标准（什么情况给满分、什么情况扣分、扣多少）
3. 判定标准必须是"可核查的"，不能是"写得好""很完整"这种无法判定的表述
4. 评分点要覆盖：实验目的与原理、算法设计与实现、复杂度分析、测试与结果、
   实验结论、报告规范

请用表格输出，并单独说明：哪些评分点最容易产生争议、为什么、该怎么缓解。
```

**4.4.2 评分 Prompt 迭代（这段的迭代记录最值钱）**

```
请帮我写一个用于"逐项评阅实验报告"的提示词。要求：

【输入】实验报告正文（纯文本）
【评分点模板】上面设计的那套
【输出】严格的结构化 JSON，不要任何解释性文字、不要 markdown 代码块包裹：
{
  "total_score": 总分,
  "comment": "总评，150-250 字，先讲整体完成情况，再讲主要问题",
  "highlights": ["亮点，最多 3 条"],
  "suggestions": ["改进建议，最多 3 条，要具体可执行"],
  "items": [
    {"name": "评分点名称", "score": 得分, "full_score": 满分,
     "reason": "判定依据，必须引用报告中的具体内容",
     "evidence": "依据出处，如 第2节/代码块L20-L80"}
  ]
}

【关键约束】
1. reason 必须基于报告中真实存在的内容，不允许编造报告里没有的表述
2. evidence 必须指向报告中的具体位置，找不到明确出处时填"未找到明确出处"并相应扣分
3. 如果报告内容与某个评分点完全无关或缺失，该项给 0 分并在 reason 中写明"未涉及"
4. 各评分点得分之和必须等于 total_score
```

**4.4.3 迭代（这是"深度"的直接证据，务必保留每轮）**

```
上一版评分结果有这些问题（附实际案例）：
- 案例1：报告里明确写了时间复杂度推导，但"复杂度分析"这项只给了 40% 的分，判错了
- 案例2：有份报告通篇没提测试，但"测试与结果"这项给了及格分，太宽松
- 案例3：三份报告的总评文字高度雷同，像是套模板

请分析这三个问题的可能原因，逐条修改提示词，并说明：
1. 每条改动是为了解决哪个问题
2. 改动可能带来什么副作用（比如变严格后误判）
3. 怎么验证改动是有效的
```

> 这段"发现问题 → 改 prompt → 说明为什么 → 验证"的完整记录，就是 25 分里含金量最高的部分。**C 每做一次质量抽检，就回来迭代一轮。**
